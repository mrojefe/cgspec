- Agent-side capabilities (issues #53 and #72, source-tested): `docs/_cgspec/capabilities.json` declares once, per project, what the agent may use beyond the repository, each with an executable check and a single approval naming capabilities. Slice prerequisites reference a `CAP-` ID; project.json `implementation_capabilities` makes a configured set mandatory for every outcome before any coding. `start ready` runs the checks, binds registry, probe-input and project-policy bytes, and fails closed on a missing, stale, unapproved, undeclared or failing capability. Doctor rejects active records that bypass the global set. A check proves only that its probe passed when run; whether a probe meaningfully exercises a browser session, model or messaging channel depends on the project's own script.
- Protected implementation branches (issue #73, source-tested): new installs declare `main` and `master` protected by default; projects may name a renamed baseline. T1+ Git plans, editor enforcement, staged implementation and doctor reject protected or detached implementation branches while still allowing their revisions as approved bases and leaving landing/release operations separate.
- Release classification is engine-backed: `cgspec_hook.py release check --target VERSION` reads the declared `release` policy from `project.json` and each included slice's `Release:` field, computes the highest required bump (treating backward-compatible deprecations as at least minor and never guessing a policy for undocumented projects), and rejects undersized targets. The trusted-installation bootstrap and a live installed-CI rehearsal remain unproven and out of scope for this gate.

- Approval provenance (#57): local staged/commit-message and CI gates require cryptographically verified host receipts for new inbox approvals; signed receipts bind the exact message, session, timestamp and repository history and cannot be replayed as another approval. An installed blocking pre-push hook checks finished approval commits and key policy changes with parent-trusted human keys, including intermediate outgoing commits. Receipt signing is an external isolated-host responsibility: no host signing service or private key provisioning is included, and stock unsigned hook payloads require the human signed-trailer fallback. Heartbeats and direct-command guards (#55/#56) remain complementary signals, not signature authorities. Source fixtures model the host signer; no real host signer or consumer upgrade has been rehearsed.

## Remaining release and adoption limits

The Git hook relocation repair is scoped to hook ownership: portable event names, current Git directory discovery and preservation of modified/symlinked hooks. It does not complete portable-reference validation, adapter drift checks, shell conformance or per-worktree ownership of shared hooks. Exact palette/theme/state conformance and installed build identity remain unimplemented; reports 42–43 in the workspace audit folder specify their reproduced gaps and proposed acceptance tests.

1. The `v0.3.0` package release includes the current source-tested capabilities. Complete the trusted installation bootstrap and rehearse the installed CI path on a repository with the required server-side protection. This package's main-origin detector is a different workflow.
2. Establish effective credential isolation or appropriate server-side protection before promising PR-only enforcement. A bot/fork is insufficient if the agent's shell can still use owner credentials. The accepted free/squash preference remains in force; private-fork permissions and the end-to-end merge flow still need validation.
3. Extend live Claude acceptance to prove `prompt_cache.requests` increases over two interactive responses; `claude -p` does not invoke the status line. Build and test Codex and Antigravity collectors where real telemetry exists. Context-pressure integration is also absent. Never infer quota from model names, turn count or context size.
4. Complete uncontaminated agent-driven design trials, desktop/phone interactions and blind visual judging. Native mobile/device behavior and cross-provider media integration require separate evidence. No general token savings or visual-quality improvement is established.

Keep blockers visible until evidence closes them. Do not turn this list into a blanket readiness claim after a passing test run.
